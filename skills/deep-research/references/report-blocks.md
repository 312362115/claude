# 调研报告组件库（report-blocks）

> 调研报告专属的输出组件——把调研结论装进合适的"块"里，组合成文档。
> 这是组件库不是模板：**有对应内容形态时调用对应组件**，没有内容就不要用。
>
> 通用组件（表格 / 列表 / Card-Grid / VS-Block / Timeline / Callout / Chart-Container / Badge / Metric-Card 等）见 `writing` skill 的 `references/components.md`，本文件不重复。

---

## 使用原则

```
内容形态  →  调用组件        ✅ 内容驱动组件
"我要写技术选型"  →  套模板  ❌ 模板驱动内容
```

- 没有 X 形态的内容就不要硬上 X 组件（没有反面证据就不要"反面观点"段，没有内部数据就不要"现状基线"段）
- 单份报告组件不要堆叠超过 8-10 种，避免"组件展示馆"
- 组件可以嵌套也可以独立——比如"结论 + 置信度"既可放在 Executive Summary 又可放在结论段
- 顺序由内容逻辑决定，不由组件清单决定

## A. 顶部信息块

### A1. 一句话核心结论

文档第一句，给最忙的读者看。

```markdown
> Dragonfly 在我们当前并发量下尚不值得替代 Redis 7，建议观察 12 个月。
```

**用于**：所有出报告的场景（最小集）。

### A2. Executive Summary（≤500 字）

面向决策者，只含结论和建议，不含论证过程。

```markdown
## Executive Summary

[一句话核心结论]

**关键发现**：
- 发现 1（数据 / 来源 [T1]）
- 发现 2（数据 / 来源 [T2]）
- 发现 3（数据 / 来源 [T1]）

**建议方向**：[行动方向，最多 3 条]
```

**用于**：复杂研究 / 超深度报告；对比类报告内容长时也建议加。

### A3. 报告头元信息表

```markdown
| 项目 | 信息 |
|------|------|
| **调研日期** | YYYY-MM-DD |
| **调研类型** | 技术选型 / 行业分析 / ... |
| **调研深度** | 派发 N 个 sub-agent，最深 L 层，参考 M 个来源 |
| **内部数据** | 已纳入 / 未纳入（标注原因） |
```

**用于**：复杂研究 / 超深度——调研投入和数据基础需要被读者看见时。

## B. 现状与基线

### B1. 现状基线块

内部数据 + 对标基准。位置在背景之后、正文分析之前。

```markdown
## 现状基线

**内部现状**：[基于内部数据源（代码库 / 文档 / BI / 监控）的当前状态，无内部数据时改为"本报告基于公开数据，未纳入内部数据验证"]

**对标基准**：[用于对比的行业标准 / 竞品水位 / 最佳实践，及其出处]
```

**用于**：所有需要"对比内外"的调研（复杂研究 / 超深度必备，对比类推荐）。

### B2. 内部数据缺失声明

简化版基线，仅一行 callout：

```markdown
> ℹ️ 本报告基于公开数据，未纳入内部数据验证。
```

**用于**：纯公开信息的轻量调研。

## C. 论证类组件

### C1. 假设验证表

把 1.6 提出的初始假设逐一对账。

```markdown
## 假设验证结果

| 假设 | 结果 | 关键证据 |
|------|------|---------|
| 假设 1：xxx | ✅ 已验证 | 证据来源 [T1] |
| 假设 2：xxx | ❌ 已证伪 | 反面证据 [T2] |
| 假设 3：xxx | ⚠️ 证据不足 | 缺什么信息 |
```

**用于**：走完整 1.6 假设流程的调研——复杂研究 / 超深度必备，对比类按需。

### C2. 反面观点与回应

```markdown
## 反面观点与回应

- **反面观点 1**：xxx（来源 [T2]）→ **回应**：[接受 / 反驳 / 承认不确定]
- **反面观点 2**：xxx（来源 [T1]）→ **回应**：...
```

**用于**：核心结论存在争议或反方证据时——复杂研究 / 超深度必备。没有反面证据就不要硬凑。

### C3. 结论 + 置信度标注

```markdown
- 结论 1：xxx（基于 yyy 数据 [T1]）｜置信度：**高**
- 结论 2：xxx（基于 yyy 对比 [T2]）｜置信度：**中** — 存在 xxx 反面证据
- 结论 3：xxx（基于 yyy 推断）｜置信度：**低** — 仅 T3 来源，待补一手验证
```

置信度评估规则见 SKILL.md 3.3。

**用于**：所有需要给读者明确决策依据的结论段。

## D. 对比/评估类组件

### D1. 多维度对比表

```markdown
| 维度 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 性能 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐ |
| 生态 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| 成本 | $$ | $$$ | $ |
```

字段示例：性能 / 生态 / 学习成本 / 运维 / 许可证 / 社区活跃度——按命题选维度，不强制。

**用于**：技术选型 / 竞品分析 / 工具评估。

### D2. 综合评分雷达

调 `diagram` skill 生成 radar 图，文字配置：

```json
{ "type": "radar", "title": "", "data": {
  "labels": ["性能","生态","成本","学习成本","运维"],
  "series": [
    {"name": "方案 A", "values": [5,4,3,4,4]},
    {"name": "方案 B", "values": [3,5,2,3,5]}
  ]
}}
```

**用于**：≥3 维度对比且需要一眼可视化时——单一维度对比用柱状图即可。

### D3. 场景化推荐表

不一刀切，按场景分推荐：

```markdown
| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 高并发 + 小集群 | 方案 A | xxx |
| 多语言客户端 + 大集群 | 方案 B | xxx |
| 已有方案 X + 性能瓶颈不在 X | 不迁移 | xxx |
```

**用于**：选型类报告——比"二选一结论"更负责任的输出形态。

## E. 过程可观测组件

### E1. 调查拓扑表

基于 `/tmp/research-topology-<timestamp>.json` 生成。让调研深度可观测。

```markdown
## 调查拓扑

| 指标 | 数值 |
|------|------|
| 命题复杂度 | simple / comparison / complex / super-deep |
| 派发 Sub-agent 数 | N（含 sub-sub） |
| 最深递归层级 | L |
| Synthesis 轮次 | R |
| 总 WebSearch | Σ search |
| 总 WebFetch | Σ fetch |

**Sub-agent 分解**：

| ID | Parent | Round | Topic | Spawn Reason | Budget Used | Findings | Status |
|----|--------|-------|-------|--------------|-------------|----------|--------|
| sub-01 | — | 1 | 子问题摘要 | 初始拆解 | 8/11 | 4 | completed |
| sub-02 | sub-01 | 2 | 深挖反面 | devils_advocate | 6/5 | 2 | completed |

**放弃的线索**（仅当 `abandoned_leads` 非空）：

- 线索 X — 反爬无法验证
- 线索 Y — 时效性不足（>5 年）
```

**用于**：走 Multi-Agent 的调研（对比类按需 / 复杂研究 / 超深度）。简单事实查询也保留最小拓扑（仅指标表）。

### E2. 数据口径说明

```markdown
> 📐 **数据口径**：本节"市场规模"采用 IDC 2026 Q1 定义——包含 SaaS 订阅 + License 销售，**不含** 硬件捆绑销售。与 Gartner 口径差异约 12%。
```

**用于**：跨来源对比、口径有歧义时——避免读者误读。

## F. 引用与来源组件

### F1. 来源分级参考资料

```markdown
## 参考资料

### 一手来源 [T1]
1. [Redis 官方 benchmark](https://redis.io/...) — p99 延迟原始数据

### 二手来源 [T2]
2. [InfoQ 对比测试](https://www.infoq.cn/...) — 多线程吞吐对比

### 三手来源 [T3]
3. [社区讨论汇总](https://...) — 用户反馈（未独立验证）

### 内部数据
4. `monitoring/redis-p99-2026q1.csv` — 内部生产数据
```

**用于**：所有出报告的场景。三级分组按实际命中来源决定——只有 T1/T2 时就不写 T3 段。

### F2. 行内引用标注

正文中用上标编号，指向末尾参考资料：

```markdown
Redis p99 通常低于 2ms[1]，Memcached 约 1.5ms[2]。
```

HTML 模式：

```html
数据描述<sup><a href="#ref-1">1</a></sup><span class="tier-badge tier-t1">T1</span>
```

**用于**：所有报告。

## H. 内容形态 → 组件 速查

| 你手上有什么内容 | 调哪个组件 |
|----------------|----------|
| 一句话能说清的核心判断 | A1 一句话结论 |
| 3-5 条要点决策者得先看到 | A2 Executive Summary |
| 调研投入数据需要被看见 | A3 报告头 + E1 调查拓扑表 |
| 内部数据 + 外部基准对比 | B1 现状基线 |
| 走完了 1.6 假设流程 | C1 假设验证表 |
| 收到了真实反方证据 | C2 反面观点与回应 |
| 多个结论且置信度不一 | C3 置信度标注 |
| 多方案多维度对比 | D1 对比表 + D2 雷达图（≥3 维度） |
| 结论不应一刀切 | D3 场景化推荐表 |
| 跨来源数据有口径差异 | E2 口径说明 callout |
| 引用了多个来源 | F1 来源分级 + F2 行内标注 |
| 大段数据 / 趋势 | Chart-Container + bridge.py（饼/柱/折/雷达/...） |
| 多角色流程 / 架构关系 | Chart-Container + capture.py（流程/时序/架构图） |
| 多发展阶段 | Timeline（writing skill） |
| 关键数字独立强调 | Metric-Card（writing skill） |
| 关键洞察打断正文 | Callout（writing skill） |

## I. 反模式

- ❌ 调研类型是"技术选型"就硬塞 D1+D2+D3 全套——只有 1 个候选方案就不要写对比
- ❌ 没有反面证据也要"反面观点"段——会逼自己编反方
- ❌ 没有内部数据也要"现状基线"——直接 B2 一行 callout 说明即可
- ❌ 结论置信度全是"高"——置信度有意义的前提是分布有差异
- ❌ 调查拓扑表里 sub-agent 编号 sub-01 到 sub-99 都填——简单事实查询只需最小拓扑
- ❌ 因为模板有"机会识别"段就硬写——没机会就不写
- ❌ 借鉴 D1 时强行凑 5+ 维度——维度按命题真正关心的来
